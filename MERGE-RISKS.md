Read-only source review on 2026-10-13 of the open redesign heads through #57 (`77566f177a660c3754611eb869b6f8bcfaabc753`), #59 (`4e36acd66ddd0fe3f2e3860a148a4a1914bc4037`), #61 (`2ead8bd12a3986b894313654dd1b78f4bd662946`), and relevant inherited code in #66 (`764b9c17c0061a6ad901218ff0078baae239599f`). ## Merge gate: filament insertion must stay armed

**The unmodified open heads do not enforce the requested invariant in the UI.** #49 adds the Pro Outputs and sensors panel. In #57, #59, and #61 it iterates every filament sensor and provides an on/off switch; its handler sends `sensorCommand(name, enabled)`. `sensorCommand` unconditionally emits `SET_FILAMENT_SENSOR SENSOR=<name> ENABLE=0` for false. The printer getter includes every `filament_switch_sensor` and `filament_motion_sensor`, with no examination of its `insert_gcode` configuration. Turning off a sensor whose insertion hook starts the load flow therefore disarms that flow unless firmware independently rejects the command. Later heads did not remove or protect this path.

Evidence:

- [ControlOutputs.vue:61-66](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/components/control/ControlOutputs.vue#L61-L66) exposes the toggle; [148-154](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/components/control/ControlOutputs.vue#L148-L154) gets all sensors and sends the command.
- [model.ts:263-265](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/services/control/model.ts#L263-L265) allows the off command; [getters.ts:416-432](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/store/printer/getters.ts#L416-L432) supplies every sensor.
- The pre-existing [RunoutSensorsCard.vue:66-72](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/components/widgets/runout-sensors/RunoutSensorsCard.vue#L66-L72) has the same unrestricted handler, so protecting only the redesigned surface leaves another route to disarm insertion.
- [model.spec.ts:170-173](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/services/control/__tests__/model.spec.ts#L170-L173) asserts an ordinary runout sensor can be disabled. It has no insertion-hook case.

Required minimal safeguard, in a separately reviewable integration-only commit or follow-up PR before the original train reaches production: identify insertion-hook sensors from the full sensor section in `configfile.config` / `configfile.settings`; present their state without an off action and refuse `enabled: false` in both panel handlers. Keep `enabled: true` available for recovery. Do not rely only on a sensor name: the invariant is attached to its `insert_gcode`, and different firmware may rename the section. Unknown configuration must not be treated as proof that disabling is safe. Preserve normal runout-only controls where the configuration explicitly establishes no insertion hook.

Focused tests: a realistic sensor with nonempty `insert_gcode` cannot emit `ENABLE=0` from either panel even when its handler is called directly; it can emit `ENABLE=1`; a confirmed runout-only sensor retains its normal off command; configuration absent/loading is conservative. UI protection cannot replace firmware policy for arbitrary G-code entered in the Console or sent by another client; the firmware hook must remain armed independently of this browser.

The new Load/Unload/Change controls themselves use the printer's published `LOAD_FILAMENT`, `UNLOAD_FILAMENT`, and `M600`-style macros, optionally passing the selected material's `TEMP`. They do not rewrite `insert_gcode`: [ControlFilament.vue:79-83](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/components/control/ControlFilament.vue#L79-L83), [98-111](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/components/control/ControlFilament.vue#L98-L111), [138-142](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/components/control/ControlFilament.vue#L138-L142). Load/Unload are disabled while printing; M600 is intentionally available for a guided mid-print change. Macro semantics and heating/purge safety remain firmware responsibilities.

## Developer mode and Pro are different

Pro is a browser-local display preference, explicitly never a permission: [pro-mode.ts:14-17](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/services/pro-mode.ts#L14-L17). More controls, Console, or Files appearing in Pro must not grant access denied by the printer.

The redesigned Developer mode page preserves these rules:

- Read manageability from `/server/aux/dev_mode`; on failure use the read-only `/server/muon/dev_mode` solely to display enabled status. A 200 HTML SPA fallback is rejected. Default the physical guard to armed unless the printer explicitly reports false. OTP recording is unknown unless the printer explicitly reports its boolean, and disarmed OTP recording is separate from disarmed physical consent: [state.ts:35-70](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/services/dev-mode/state.ts#L35-L70).
- With the guard armed, fetch the printer's current waiver and version, open its short-lived challenge, poll through Moonraker's aux proxy, and redeem only after `confirmed`; refusal stops the wait. Enable sends waiver acknowledgment, version, and challenge ID. Guard explicitly false permits `{ enabled: true }`. Disable sends `{ enabled: false }` without a challenge so exit does not depend on a working knob: [DeveloperModeSettings.vue:283-348](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/components/settings/DeveloperModeSettings.vue#L283-L348), [365-412](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/components/settings/DeveloperModeSettings.vue#L365-L412).
- Editable config comes from the developer copy; with mode off, macros open from `defaults` where registered. Config is suppressed from the Files list unless mode is on; deep-linked config files are read-only when mode is explicitly false: [MacroEditList.vue:108-117](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/components/settings/macros/MacroEditList.vue#L108-L117), [Configure.vue:234-266](https://github.com/Muon-3D/Muon3D_Fluidd/blob/77566f177a660c3754611eb869b6f8bcfaabc753/src/views/Configure.vue#L234-L266).

Existing `DeveloperModeSettings.spec.ts` covers status, OTP text, malformed HTML, waiver and physical confirmation, refusal, guard explicitly false, and unconditional disable. It does not assert a successful read-only status fallback: its HTTP mock supplies only the consent `post` method. `services/dev-mode/__tests__/consent.spec.ts` covers the proxy route and unsafe IDs.

Risk gap: `devModeState` is one global observable without a printer key and deliberately retains last-known enabled status on failure. Macro editability uses `enabled !== false`, and deep-link readonly also checks only explicit false. Backend root permissions remain essential during unknown/stale state; the current mock tests do not establish safety across a printer switch or a delayed response from the previously selected printer. Do not mistake local Pro or stale UI state for authority to edit OEM files. Verify frontend requests against the deployed Moonraker/Aux rules before a later deployment; this task does not access either printer.

### Runtime behavior and remaining risks
